# Frontend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `services/frontend`, the grower's web app: farms and plots on `/`, today's recommendation and the 7-day plan on `/plots/{id}`, and a status line for the three services.

**Architecture:** A Next.js App Router app. Pages are thin Server Components. All service calls live in `src/lib/` and return a typed `Result`, never throw for an upstream failure. Presentational components take plain props, so they are tested without a server. The visual design comes from a design plan made with the `frontend-design` skill and approved by the learner before any UI code (Task 7).

**Tech Stack:** Next.js (App Router, TypeScript), Tailwind CSS, shadcn/ui, Vitest, React Testing Library, jsdom. Node 22.

**Spec:** `docs/superpowers/specs/2026-11-18-frontend-design.md` (requirements in `tasks/p2.md`, section "The `frontend`"). Read both before starting.

## Global Constraints

- The browser never calls a service. No route handlers, no client-side fetching. Pages fetch on the server.
- All calls to the services live in `src/lib/`. URLs come from `REGISTRY_URL`, `WEATHER_URL`, `PLANNER_URL`; the timeout from `REQUEST_TIMEOUT_MS`. They are in `.env.local` (never committed); `.env.example` is committed and complete.
- A missing or invalid variable stops the app with a message naming the variable. No defaults in code.
- No other pages or features than the spec lists. The only extra file is `src/app/error.tsx` (a boundary so an unexpected error is never a blank page or a stack trace).
- The frontend never computes or adjusts an irrigation number. It shows the planner's numbers. The only transformation allowed is display formatting (Task 6).
- Every fetch uses `cache: "no-store"`.
- Never read `.env` or `.env.local` files. Do not show service URLs or ports to the user.
- An invalid answer from a service (wrong shape, wrong types, non-finite numbers, empty `days`) is treated as that service being unavailable. Never repaired or defaulted.
- Tests use a fake `fetch` (`vi.stubGlobal("fetch", ...)`), never a real network.
- Commit `services/frontend` without `node_modules/`, `.next/` or `.env.local`; check `git status` before each commit.
- Small commits on branch `p2`. Never push or open a pull request without asking the learner.
- Decisions go only in `docs/judgment-log-p2.md`, and only after the learner confirms the wording (CLAUDE.md rules 8 and 9). Do not write entries yourself; stop and propose them.
- Explain each file to the learner as it is created (CLAUDE.md rule 10). The learner is a C# / Unity developer new to Next.js and React: connect ideas to C# where it helps.
- Commit messages end with the attribution line from the session's system reminder.

## Review Focus

1. **A plan with `days: []`, a missing field, or a non-finite number.** Expected: treated as planner unavailable. Never "No irrigation today" from an empty plan. (Task 4)
2. **A plot id with odd characters, such as `../health` or `a b`.** Expected: encoded into the URL (`encodeURIComponent`), so it cannot reach another path. (Task 4)
3. **A `/health` answer that is `200` but not `{"status":"ok"}`.** Expected: the service shows as down. (Task 5)
4. **Today's `run_minutes` small but above 0 (for example 0.3).** Expected: it still reads as watering, never as "No irrigation today". (Task 6)
5. **A plot whose `farm_id` matches no farm in the list.** Expected: the page does not crash. The plot is not shown under any farm, and is not dropped silently without a count. (Task 4 and 9)

### Task 3: The HTTP helper

**Files:**
- Create: `services/frontend/src/lib/types.ts`, `services/frontend/src/lib/http.ts`, `services/frontend/tests/lib/http.test.ts`

**Interfaces:**
- Produces in `types.ts`:
  ```ts
  export type ServiceName = "registry-service" | "weather-service" | "planner-service";
  export type ServiceError = {
    service: ServiceName;
    kind: "unreachable" | "timeout" | "bad-answer" | "problem";
    status?: number;   // HTTP status, for kind "problem"
    code?: string;     // problem+json `code`
    detail?: string;   // problem+json `detail`
  };
  export type Result<T> = { ok: true; data: T } | { ok: false; error: ServiceError };
  ```
- Produces in `http.ts`:
  ```ts
  export async function getJson(service: ServiceName, url: string): Promise<Result<unknown>>;
  ```
  It reads `requestTimeoutMs` from `getConfig()`.

- [ ] **Step 1: Write failing tests** with a stubbed `fetch`: a `200` JSON body gives `{ok: true, data}`; the call uses `cache: "no-store"`; a network error gives `kind: "unreachable"`; a call that exceeds the timeout (fake `fetch` that waits for the abort signal) gives `kind: "timeout"`; a `503` with `application/problem+json` body `{code: "UPSTREAM_UNAVAILABLE", detail: "weather-service is unavailable: ConnectError"}` gives `kind: "problem"`, `status: 503`, that `code` and `detail`; a `404` problem body likewise; a non-2xx with a body that is not JSON gives `kind: "problem"` with `status` and no `code`; a `200` with a body that is not JSON gives `kind: "bad-answer"`.
- [ ] **Step 2: Run** `npm test -- http`. Expected: FAIL.
- [ ] **Step 3: Implement** `getJson` with `AbortSignal.timeout(timeoutMs)`. It never throws for an upstream failure. A problem `detail` is passed through only when it is a string.
- [ ] **Step 4: Run** `npm test`. Expected: PASS.
- [ ] **Step 5: Commit:** "Add the HTTP helper that turns every failure into a typed result".
